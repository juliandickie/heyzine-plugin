# Heyzine API Audit

Dated, additive log of verified facts about the Heyzine API and MCP server. Each probe gets its own section below; earlier sections are never rewritten.

## Probe 2026-09-15

Probed against the operator's the reference account account with the saved key. Local-only artifacts (full schemas, downloaded skills) live under `docs/reference/` and are not part of this tracked log.

- Hosted MCP server at `https://heyzine.com/mcp` reports serverInfo `heyzine 1.7.0`. Streamable HTTP, POST only, JSON responses, no SSE, no sessions. Auth is `Authorization: Bearer <api key>` or OAuth 2.1 PKCE (dynamic registration, scope `mcp`); OAuth tokens work on MCP only, never on REST.
- The server exposes 20 tools, three more than the public developers page documents - `heyzine_replace_flipbook_pdf` (restricted, needs a paid plan and support enabling the account), `heyzine_search_text` (full-text search across the account, returns flipbook short id, page and snippet) and `heyzine_page_text` (plain text of one page).
- MCP tool results are markdown prose meant for chat. REST results are JSON. Only REST `flipbook-details` returns `tags`, `private`, `links.custom` and the `oembed` object. REST `flipbook-list` returns an array with `id, date, title, subtitle, description, private, size, pages, links` and no `tags`.
- REST errors arrive as HTTP 200 with a body shaped `{"success":false,"code":403,"msg":"..."}`. An invalid key gives `msg` of "Invalid user or api key". REST `flipbook-details` rejects a short id or a public URL, full ids only, and gives `msg` of "Unauthorized" for anything shorter. Unknown endpoints return an HTML 404 page rather than this JSON shape.
- `flipbook-replace` exists as an endpoint but answers "Private API endpoint. Contact support@heyzine.com for more details." on the the reference account account. There is no REST endpoint name for search text or page text, both go through the MCP endpoint with the same Bearer key.
- REST `convert` requires a `client_id` parameter as well as the API key; the key alone is not accepted.
- Ids. A full id is 40 hex characters plus `.pdf` for flipbooks, or 40 hex characters for bookshelves. Every id-taking tool also accepts the public URL, the 10-character short id, or the custom URL path, but REST `flipbook-details` is the one endpoint that insists on the full id (see above).
- The account's 105 existing flipbooks all report `heyzine.com` links (`links.custom == links.base` for all of them), but the same short id also serves correctly on the white-label host `docs.aflip.in` - verified 200 on `https://docs.aflip.in/<short>.html` for an id also present in the account listing. Academy links resolve the short domain to docs.aflip.in.
- `heyzine_convert_pdf_async` and `heyzine_convert_pdf` accept `replace: true`, which reconverts and overwrites the existing flipbook for the same URL while keeping its id. Conversion is otherwise idempotent per URL (converting the same URL twice returns the same flipbook). Async state values are `started`, `processed` and `failed`; polling is calling the same tool again with the same URL, there is no separate status endpoint.
- The account is on the Premium plan - bookshelves are available (8 exist), custom URL support is available, and `flipbook-replace` is not enabled for this account despite existing as an endpoint. The full plan gates table (which feature needs which plan tier) is recorded in the design spec, section 2, and is not repeated here.
- The leads webhook, configured in the account UI, POSTs a payload shaped `{data: {id_webhook, date, leads: [{date, first_value, second_value, flipbook: {id, title}, answer: [{label, value}]}]}}` to a URL the account owner hosts. The plugin documents this payload; it does not host a receiver.
- The link-conversion URL form `https://heyzine.com/api1?pdf=<url>&k=<client id>` needs only the client id (not the secret key) and converts on first visit.
