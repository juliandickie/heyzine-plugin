# Heyzine API Audit

Dated, additive log of verified facts about the Heyzine API and MCP server. Each probe gets its own section below; earlier sections are never rewritten.

## Probe 2026-09-15

Probed against the reference account with the saved key. Local-only artifacts (full schemas, downloaded skills) live under `docs/reference/` and are not part of this tracked log.

- Hosted MCP server at `https://heyzine.com/mcp` reports serverInfo `heyzine 1.7.0`. Streamable HTTP, POST only, JSON responses, no SSE, no sessions. Auth is `Authorization: Bearer <api key>` or OAuth 2.1 PKCE (dynamic registration, scope `mcp`); OAuth tokens work on MCP only, never on REST.
- The server exposes 20 tools, three more than the public developers page documents - `heyzine_replace_flipbook_pdf` (restricted, needs a paid plan and support enabling the account), `heyzine_search_text` (full-text search across the account, returns flipbook short id, page and snippet) and `heyzine_page_text` (plain text of one page).
- MCP tool results are markdown prose meant for chat. REST results are JSON. Only REST `flipbook-details` returns `tags`, `private`, `links.custom` and the `oembed` object. REST `flipbook-list` returns an array with `id, date, title, subtitle, description, private, size, pages, links` and no `tags`.
- REST errors arrive as HTTP 200 with a body shaped `{"success":false,"code":403,"msg":"..."}`. An invalid key gives `msg` of "Invalid user or api key". REST `flipbook-details` rejects a short id or a public URL, full ids only, and gives `msg` of "Unauthorized" for anything shorter. Unknown endpoints return an HTML 404 page rather than this JSON shape.
- `flipbook-replace` exists as an endpoint but answers "Private API endpoint. Contact support@heyzine.com for more details." on the reference account. There is no REST endpoint name for search text or page text, both go through the MCP endpoint with the same Bearer key.
- REST `convert` requires a `client_id` parameter as well as the API key; the key alone is not accepted.
- Ids. A full id is 40 hex characters plus `.pdf` for flipbooks, or 40 hex characters for bookshelves. Every id-taking tool also accepts the public URL, the 10-character short id, or the custom URL path, but REST `flipbook-details` is the one endpoint that insists on the full id (see above).
- The account's 105 existing flipbooks all report `heyzine.com` links (`links.custom == links.base` for all of them), but the same short id also serves correctly on the white-label host `the white-label host` - verified 200 on `https://<account>.aflip.in/<short>.html` for an id also present in the account listing. Academy links resolve the short domain to the white-label host.
- `heyzine_convert_pdf_async` and `heyzine_convert_pdf` accept `replace: true`, which reconverts and overwrites the existing flipbook for the same URL while keeping its id. Conversion is otherwise idempotent per URL (converting the same URL twice returns the same flipbook). Async state values are `started`, `processed` and `failed`; polling is calling the same tool again with the same URL, there is no separate status endpoint.
- The account is on the Premium plan - bookshelves are available (8 exist), custom URL support is available, and `flipbook-replace` is not enabled for this account despite existing as an endpoint. The full plan gates table (which feature needs which plan tier) is recorded in the design spec, section 2, and is not repeated here.
- The leads webhook, configured in the account UI, POSTs a payload shaped `{data: {id_webhook, date, leads: [{date, first_value, second_value, flipbook: {id, title}, answer: [{label, value}]}]}}` to a URL the account owner hosts. The plugin documents this payload; it does not host a receiver.
- The link-conversion URL form `https://heyzine.com/api1?pdf=<url>&k=<client id>` needs only the client id (not the secret key) and converts on first visit.

## Live spike 2026-09-15 (evening, main session)

Run against the reference account with the built CLI (commit e195e54 and later), one throwaway flipbook kept for later checks.

- Staging. Folder a staging folder created in a shared drive (id <folder id>). A one-page test PDF uploaded as file id <file id>, shared anyone-with-link reader.
- Drive URL forms. `https://drive.usercontent.google.com/download?id=<id>&export=download` answers 206 to a ranged GET with `content-type: application/octet-stream` and no Location header (serves the bytes directly). `https://drive.google.com/uc?export=download&id=<id>` answers 303 to the usercontent URL. The usercontent form is the plugin default; the uc form is the documented fallback.
- Conversion. `heyzine convert <url> --wait` - first poll `started`, second `processed`, 7 s, 2 polls, id <id>.pdf. The async response reports `url` on the account's white-label host (https://<account>.aflip.in/<short>.html) while `flipbook-details` reports `links.custom` and `links.base` on heyzine.com; both serve (200).
- Idempotency. A second `convert` on the same URL with no replace returns `processed` and the same id at once.
- Register. Tags and the private note sent at convert time come back verbatim from `flipbook-details`. `heyzine details <short id>` resolves through the live list because REST needs the full id.
- oEmbed. `oembed` returns the iframe for the heyzine.com URL.
- Pagination. REST `flipbook-list` honours `limit` and `offset` (limit 3 offset 0 and limit 3 offset 3 return disjoint sets), so the inventory refresh pages safely at 200.
- Replace. The Drive file was overwritten in place (same id, same URL) three times. `replace: true` on REST `/async` and on the MCP `heyzine_convert_pdf_async` tool returned `processed` in one poll and left the stored PDF unchanged. `replace: true` on the MCP blocking tool `heyzine_convert_pdf` reconverted (stored PDF became revision 2, `links.pdf` suffix `-1`). `replace: true` on REST `/rest` (blocking) reconverted in 6.2 s (stored PDF became revision 3, suffix `-2`). The id, both public URLs, the title, the tags and the private note survived every replace. Conclusion: replace is honoured only by the blocking endpoints; the CLI routes `--replace` through `/rest`.
- Page text. `heyzine_page_text` reflected the old edition for some seconds after the blocking replace (search index lag); `links.pdf` with a cache buster is the reliable check.
- Housekeeping. The scratch `mcp-remote.headers` written by the Task 10 handshake was deleted; the launcher now removes the file on exit.

## First real batch 2026-09-15 (night, session)

Run against the reference account with the 0.1.2 build - 37 academy PDFs converted from their the source site's wp-content URLs. Findings, all reproduced at least twice.

- Private note cap is 200 characters. `flipbook-design` answers HTTP 500 to a 201 character `private_note` and "Flipbook updated" to 200 (probed 200, 201, 205, 210 to 400). The async convert is worse - a note over the cap does not fail the conversion, it silently drops the title, tags, private note and template from the record, so the flipbook converts untitled with the account default design. 34 of the 37 batch rows landed that way because the generated note (source_name, source_url, idd_to, embedded, published, published_by) ran 280 to 453 characters with academy URLs. A 453 character note answered HTTP 500 from `/async` instead. Fixed in 0.1.3 - `buildRegister` trims `published_by`, then `source_url`, then `source_name` until the note fits, every outgoing note is asserted, and the batch results carry a `register` column.
- Newlines and URLs inside `private_note` are fine on `flipbook-design`; only length matters.
- Settle lag. After `/async` answers `processed`, `flipbook-details` and `flipbook-list` return an empty title, empty tags and empty note for several minutes (empty at 20 s, populated by about 10 min on a 26 page PDF), and the rendered page shows the default design for the same window. `flipbook-design` changes are visible on the rendered page within seconds. The plugin now polls details until the title matches (10 s interval, 5 min budget) before reporting.
- `flipbook-design` accepted `template`, `title`, `tags`, `private_note`, `download`, `share`, `full_screen`, `prev_next` and `show_info` in one PATCH on all 37 books; that is the repair path when a conversion lands without its design.
- The page `<title>` shows the requested title even when the record's `title` is empty, so the browser tab is not proof the title was stored; read `flipbook-details`.
- Conversion times varied widely for similar PDFs - most 8 to 30 s, one 8 page 2.4 MB file took 75 polls (about 6 min) at 11:40, then the batch converted 33 files in 5 minutes two at a time. One `/async` call answered HTTP 500 on two attempts a minute apart for a 2.0 MB PDF whose note was 453 characters; the same file converted at once with a short note.
- A wp-content URL that answers 404 with an HTML page still "converts" - Heyzine rendered the source site's sign-in page as an 8 page flipbook (id <short>, created by a probe with the wrong URL; delete gated to the operator). HEAD every source for `application/pdf` before converting.
